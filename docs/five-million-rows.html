As-Subkī Books D1 read budget 25 Sep 2026

Five Million Rows

The shop went offline for an hour because the database ran out of its daily allowance. Here is where every row went, and the plan to make a page view cost nothing at all.

What happened

The allowance ran out, and D1 stopped answering

D1's free plan allows 5,000,000 rows read per day. On 24 September that ceiling was passed, and D1 refused every query for about an hour — account-wide, including from the command line. Every page that touches the database failed at once.

Nothing was broken and nothing was misconfigured. The shop simply asks the database more questions than the allowance permits, and a crawler asked a great many of them in one day.

Already shipped

Three fixes went out during the outage: noindex on every filtered catalogue view; robots.txt now blocks the filtered URLs entirely; and the shop shows a proper “Back shortly” page at 503 instead of a raw error when the database is unreachable. Those stop the surge. They do not move the ceiling. That is what this plan is for.

The measurements

Five queries are the entire budget

Measured over seven days with wrangler d1 insights. These five account for essentially all of a 13,071,980-row week — about 1.87M a day, 37% of the allowance.

Efficiency is rows returned divided by rows read. The bottom four read around 1,200 rows to return a single number or one page of 24 books. The catalogue holds under 300 books, so each of these reads the whole shop roughly four times over to answer one question.

Four of the five share one shape — the shelf lookup c.path = ? OR c.path LIKE ? || '/%', which no index can serve. That family alone is 72% of all reads. The roll-up is the other 28%.

Worth being clear about

The roll-up has already been optimised once, from 34,700 rows per call down to 1,658, and it has a 60-second cache. But that cache is a variable in memory, and Workers run many short-lived isolates, so each cold one pays full price. It still ran about 312 times a day. The problem is not a slow query — it is that cost is tied to traffic.

The idea

Count the shop once, then write the answer down

Today, every time someone opens a shelf page the Worker counts the whole shop from scratch — reads every book, every shelf link, works out the totals, throws the answer away, and does it again for the next visitor.

Instead: build one snapshot of the catalogue — about 300 books, roughly 200KB of JSON — keep it in Cloudflare KV, and let every page read that one shared copy. Filtering, counting, sorting and pagination all happen in the Worker over 300 objects, which costs microseconds and no database reads at all. The database is touched only when something actually changes: a listing edited, or an order placed.

The shift that matters is what the cost is tied to. Traffic is the thing nobody controls — a crawler decided the 24th, not customers. Edits are the thing the owner controls, and there are a few dozen a day.

Search is the one real exception

listBooks has two modes. Without a search term it filters and counts — that is what the snapshot replaces. With one, it joins books_fts and uses FTS5 ranking, Arabic normalisation and diacritic folding. None of that can be reproduced by filtering 300 objects in JavaScript, and trying would quietly make search worse — the thing customers use most deliberately.

So the function keeps both paths: a search term goes to D1, no search term goes to the snapshot. That is affordable now, because search is noindex and robots-disallowed, so crawlers no longer walk it. If search becomes the new top consumer after this lands, the answer is caching result sets per query string — not reimplementing FTS.

Design

How the snapshot is built and kept honest

What it holds

Enough to answer every catalogue question without a second read: id, slug, title, Arabic title, language, publisher, price, sale percent, stock, reserved, shipment, multi-buy, cover key — and paths, every shelf the book sits on, already resolved.

That last field is what kills the expensive lookup. A descendant test stops being OR against LIKE in SQL and becomes p === path || p.startsWith(path + '/') in JavaScript, over 300 objects.

Where it lives

Cloudflare KV. There is no KV namespace configured yet — the SESSION line in the build output is Astro's own sessions warning, not a binding. One needs creating and adding to wrangler.jsonc. The free tier allows 100,000 reads and 1,000 writes a day; reads are one per page view and writes one per change, so both sit far inside.

If KV misses or returns malformed JSON, fall back to reading D1 directly. A cache that cannot fail safely is a second outage waiting.

Invalidation rides the pattern that already exists

forgetCategoryCounts() and forgetHomeRows() are already called from every place that changes the catalogue — four sites in book-deletion.ts, the shelf move and create endpoints, and the listing editor. That wiring is correct today. It only needs to bump a version token rather than clear a local variable, exactly the way IMAGE_VERSION already works for covers. The snapshot key carries the version, so a bump invalidates globally with no purge and no race.

The one gap in that wiring

Placing an order changes reserved without going through the listing editor, so it never calls those functions. Left alone, displayed stock would drift over a busy day. The bump has to be added where stock is reserved — plus a five-minute TTL as a backstop against any other missed bump.

Effect on customers

Same pages, one narrow trade-off

Nothing changes in what a customer sees or can do: same filters, sorting, counts and prices, and faster if anything, with no database round-trip in the render path. There is no schema change and no migration.

The one behavioural difference is that stock figures could be stale for up to the TTL if a bump were ever missed. That matters less than it sounds, because it is already true — checkout re-reads availability from D1 and refuses a copy that has gone. A customer can today add a book that sells out while they are deciding. This widens that window from seconds to at most a minute, and it is caught in exactly the same place.

Doing it

Steps

  1. Create the KV namespace and bind it in wrangler.jsonc.
  2. Write src/lib/catalogue-snapshot.ts — build from one D1 read, get-with-fallback, version token, TTL backstop.
  3. Point the customer-facing readers in db.ts at it. Keep one implementation of the filtering logic fed from either source — forking it is how the portal and the shop drift apart.
  4. Bump the version in forgetCategoryCounts / forgetHomeRows, and at order placement.
  5. Cache sitemap.xml off the same snapshot.
  6. Test, deploy, then measure.

Testing

  • Full npm run test:e2e — the baseline to beat is 1,122 passed, 0 failed. Run it in the background; a 600-second foreground limit truncates it and reports a false timeout.
  • Negative controls, as used throughout this work: break the invalidation and prove a test fails; serve a deliberately stale snapshot and prove checkout still refuses a sold copy.
  • New assertions worth having: an edit is visible to a customer on the next load; an order moves the displayed stock; a corrupt snapshot falls back to D1 rather than erroring; shelf counts match the D1 answer exactly, for every shelf.
  • Confirm the portal still reads through to D1 — change a price, see it at once.

Done when

The snapshot serves every customer catalogue page; d1 insights no longer shows those five queries at the top; rows_read_24h sits in the low tens of thousands on a normal day; the full suite is green; and the portal behaves exactly as before.

What this touches

Every file the change opens, and the one shared seam

Checked from the owner's side as well as the customer's. The portal is not being cached — but two of its screens call the same functions the catalogue does, and one of them matters.

Highlight — the one real overlap

admin/books/[id].astro:41 — the listing editor calls categoryCounts() to show how many books sit on each shelf. That is the same function the catalogue uses, and the 28%-of-budget one this plan repoints at the snapshot. Left alone, the owner would move a book between shelves and see the old counts. This call site must keep the D1-backed path. It is the only place in the portal where that is true, and it is the single easiest thing to get wrong in this change.

Checked and clear: admin/sales/[id]/preview.astro calls saleBooksFor, which is an owner-only function and not on the repoint list. The one saleBooks mention in api/admin/sales/index.ts is inside a comment, not a call. Nothing else in admin/, api/admin/, admin-db.ts or dashboard.ts touches a function this plan changes.

What changes significantly

  • Where customer catalogue data comes from — D1 on every request becomes one shared snapshot. This is the point of the change, and the thing to watch in testing.
  • Stock can be briefly stale on customer pages if a version bump is ever missed. Checkout still refuses a sold copy, so the failure is caught where it is caught today.
  • Order placement gains a cache-invalidation responsibility it does not have now. New coupling between the order path and the browsing path — worth a test of its own.

What does not change

  • The portal reads D1 directly, exactly as now — including the shelf counts in the listing editor, provided the seam above is handled.
  • Checkout, orders, /order/<ref>, shipments, Telegram and the hold sweeper are untouched.
  • No schema change, no migration, nothing to roll back in the database if it has to be reverted.

Held in reserve

Two things deliberately not in this change

A closure table for shelf descendants would turn the OR/LIKE into an index probe. It needs a migration and sync logic, and it is largely redundant once the snapshot lands.

Edge-caching the HTML is a bigger lever still — but it has a real prerequisite. Every public page carries a per-request CSP nonce. Caching the HTML would either reuse one nonce across visitors, weakening the CSP that was deliberately built to drop 'unsafe-inline', or desynchronise the header from the body and break the inline scripts. Those scripts would have to move to hashes or external files first. Separate work.

Scope discipline

Shipments, orders, checkout and the portal are all explicitly out of scope. They are correct today and are not what spent the budget. Touching them would put the order path at risk to fix a browsing problem.

Afterwards

What to watch

Crawlers take days to re-read robots.txt, so rows_read_24h will fall gradually rather than at once. Worth checking over the next few days with wrangler d1 info assubki-books, and again a week after the snapshot ships to confirm those five queries have left the top of d1 insights.
